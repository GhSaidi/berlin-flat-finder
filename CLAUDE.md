# Berlin Flat Finder: project guide for Claude Code

## Context
Built at **AI Builders × commIT Hack Day Berlin** (20 November 2026). Theme: "Build something useful with AI."
Submission: a demo video, the GitHub repository and a URL of the deployed app.

## The idea
A semantic flat finder for Berlin. The user describes the flat they want in plain language
("quiet 2-room flat near a park, good for working from home") and sets filters (max price,
min rooms, district). The app returns the best-matching listings from a PostgreSQL database.
The data is ~200 **synthetic** listings generated by a script (this version never scrapes real sites;
see "Future direction").

PostgreSQL is the core of the project: it stores the data, the embeddings (pgvector),
the relational model, the full-text index and the search log. It is built in 3 milestones,
each one a working, demoable app on its own, and each split into two tasks:

| Milestone | What it adds | Tasks |
|---|---|---|
| M1 | Semantic + filter search with pgvector, Streamlit UI | 1a, 1b |
| M2 | Districts table + JOINs + stats view; full-text + vector hybrid ranking | 2a, 2b |
| M3 | An OpenAI model writes a recommendation from retrieved listings; search log | 3a, 3b |

At the start of a session, run `git tag` and `git log --oneline -5` to see which checkpoints exist.

## Project status

  M2 and M3 are planned but not built.
- `main` is the deployed state. The `m1` tag points one step earlier: two later commits relaxed the uv and Python
  pins so Streamlit Community Cloud can install the app. The database is unchanged since `m1`.
- Open items in this repository: the optional vague-query hint (see README → Roadmap), an OS sandbox for
  Claude Code, and extended guardrail tests.
- Current weak spots are listed in README → Known limitations. Read them before proposing new work.

## Future direction
Further development is planned as a new version (e.g. a fork) aiming at a production MVP. README → Roadmap lists the
goals: legally collected real data, a Next.js/React frontend with a Python API, a data layer for large volumes, and
richer AI features. In that version:
- **Hackathon-scope rules get revisited:** synthetic data only, Streamlit as the UI, OpenAI as the only provider,
  and the milestone/checkpoint workflow above.
- **Data collection rules that apply from day one:** prefer open data and official APIs over scraping; scrape only
  where a site's terms and robots.txt allow it, with rate limits and an identifying user agent; collect no personal
  data beyond what is needed (GDPR); document every source and its license.
- **Rules that stay:** additive, numbered migrations; secrets only in environment variables; PostgreSQL + pgvector
  as the core unless measurements show it no longer fits.

## Development guidelines
- Work in small steps: before each step, state what will change and why, and wait for approval.
- Prefer simple, readable code over clever code. Stick to the stack below.
- Ask before adding any package, and add packages only with `uv add <pkg>` (never pip, never edit versions by hand).
- Secrets only in `.env` (never in code, never committed).
- If something fails twice, stop, summarize the problem and propose options.
- Git operations (`git add`, `commit`, `push`, `tag`) are run manually by the developer; Claude suggests the exact commands.

## Checkpoints and reverting
- Branch `dev` is where work happens. `main` only holds finished, working checkpoints.
- After each finished, demoable task, `scripts/checkpoint.sh <tag>` saves a database snapshot
  (`snapshots/<tag>.sql`) and prints the git commands to commit, fast-forward `main`, tag and push.
  Tags in order: `m1`, `m2a`, `m2b`, `m3a`, `m3b`.
- To go back: reset the code to the tag with git, then `scripts/restore.sh <tag>` restores the database snapshot.
- In practice: `snapshots/m1.sql` (from `scripts/checkpoint.sh m1`) also seeded the hosted Neon database;
  `scripts/restore.sh` was never needed. The scripts call `psql` inside the Docker container, so no local
  PostgreSQL client is required.

## Database rules
- **Additive changes only.** Never DROP or RENAME a table or column. Older code must keep working
  against a newer database.
- Every schema change is a new numbered, idempotent file in `sql/` (`IF NOT EXISTS`,
  `CREATE OR REPLACE`), applied with `scripts/migrate.sh`.
- The app connects with the URL in `.env` (`DATABASE_URL`).

## Security rules
- Never hardcode API keys or passwords. Read them from environment variables (`os.getenv`, loaded from `.env`).
- Never use `eval()` or `exec()`.
- Ask before adding new network calls. The app's expected calls are PostgreSQL and the OpenAI API;
  any other external request needs explicit approval.

## Claude Code guardrails
`.claude/` holds this project's guardrails. Only a human edits `.claude/settings*.json` and `.claude/hooks/`;
Claude proposes changes as exact text.
- **Permissions** (`.claude/settings.json`): deny reading or editing secrets (`.env` files, keys, `~/.ssh`,
  `~/.aws`), editing `uv.lock`, `snapshots/` and `.git/`, deleting files, network tools and force pushes.
  Ask before `git commit`, `git push`, `git reset --hard`, `git restore`, `docker`, the `scripts/` and `seed.py`.
- **Hooks** (`.claude/hooks/`): `protect-files.sh` confines file tools to the project, `~/.claude` and
  Claude Code's temp folder, and blocks secrets and write-protected files. `validate-commands.sh` blocks
  deletions, destructive SQL and other risky Bash patterns, and forces a prompt for Docker, git operations
  that record or discard work, the checkpoint/restore/migrate scripts (their inner commands are
  invisible to the hook), `seed.py` (paid API) and paths outside the project. Both fail closed and target `/bin/bash` 3.2.
- **Testing the guardrails**: `bash .claude/hooks/test-hooks.sh`, run by a human from the repository root.
  The tested commands are strings and are never executed.
- No OS sandbox is configured yet (planned).

## Stack
- **Python 3.12** (`.python-version`, minor version only) managed with **uv** (developed with 0.13.7).
  No exact uv or Python patch pin: Streamlit Community Cloud installs with its own uv and Python 3.12 build.
  Dependencies live in `pyproject.toml`; `uv.lock` is committed. No requirements.txt, no pip.
- **The virtual environment is `venv/`, not `.venv/`**, via `UV_PROJECT_ENVIRONMENT=venv`
  (set in `.claude/settings.json`). Never create or use `.venv`. Run uv commands from the project root.
- Streamlit (UI), psycopg 3 + `pgvector` Python package, ruff (dev: lint/format)
- PostgreSQL 17 + pgvector in Docker (`compose.yaml`, image `pgvector/pgvector:pg17`).
  Local connection: `postgresql://postgres:postgres@localhost:5432/flats`.
- **OpenAI API only** (official `openai` Python SDK), key in `.env` as `OPENAI_API_KEY`:
  - Embeddings: `text-embedding-3-small` → **1536 dimensions** (`vector(1536)`), model name from `OPENAI_EMBEDDING_MODEL`
  - LLM (M3 only): Responses API (`client.responses.create`), model name from `OPENAI_CHAT_MODEL`
- **Out of scope for now:** other LLM providers and local/open-source embedding models.

## Deployment
- App: Streamlit Community Cloud, deployed from `main` (`app.py`, Python 3.12); every push to `main` redeploys.
- Database: Neon (hosted PostgreSQL 17 + pgvector), direct (non-pooled) connection URL with `sslmode=require`,
  loaded from a `snapshots/<tag>.sql` dump.
- Secrets live only in the Streamlit app settings (TOML): `OPENAI_API_KEY`, `OPENAI_EMBEDDING_MODEL`, `DATABASE_URL`.
- Schema changes must also be applied to the hosted database before pushing code that needs them.

## Commands
```
uv sync                          # create/update venv/ from pyproject.toml + uv.lock
uv run python generate_data.py   # run any script inside the project environment
uv run python seed.py
uv run streamlit run app.py      # start the app
uv run ruff check . && uv run ruff format .
uv add <package>                 # only after approval
docker compose up -d             # start Postgres
scripts/migrate.sh               # apply SQL migrations
```
